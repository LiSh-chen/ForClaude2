# 鄉鎮特色內容作業流程（SOP v3.4）

v2 之後的檢討結論：流程裡凡是「需要負責人決定」的地方，都表示 SOP 少了一條**決議規則**。v3 的目標是：**負責人只定價值觀與規則；個案一律由規則決定；負責人只看結果與自動決議清單，需要時可以推翻。**

## 0. 授權與原則
1. **SOP 本身就是授權**：撰寫者可以依本 SOP 對全部縣市依序執行，不需要逐批詢問「要不要做」。
2. 只有第 6 節的「停止條件」發生時才可以問負責人；其餘情況一律走第 4 節決議表。
3. 內容檔的任何修改都必須走第 8 節的「原子化操作」（先驗證、後提交）。
4. 外部意見（其他 AI、搜尋摘要、使用者的截圖）都是**線索**，必須經第 3 節的證據標準驗證才可寫入。
5. **優先序**：本 SOP 與 `REVIEW_HANDBOOK.md` 衝突時以 SOP 為準，撰寫者須在同批次於手冊註記「依 SOP §x 修訂」。已知衝突的處理：手冊三.1「C 級不收錄」改為「僅單一來源傳說可依 E3 收錄，其餘 C 級不收錄」；手冊六.4／七「先確認／全 PASS 才交付」改為「依第 5 節交付後可被負責人推翻」；手冊「三者缺一刪除」受 D10 約束；手冊八.1 稱號同義詞以 D13 為準。
6. **通用搜尋額度**：每個 FAIL 每輪最多追加 3 次搜尋（不同關鍵字）；D4、D5、D7、D16 與 S3 都在此額度內。輪次以「條目」為單位計。

## 1. 角色
| 角色 | 誰 | 職責 | 不得 |
|---|---|---|---|
| 撰寫者 | 主 Claude | 建候選池、評分、寫句子、依決議表處理 FAIL、維護台帳、交付 | 自己宣布通過 |
| 研究員 | subagent（每縣市一個，可平行） | 只做候選池 | 寫最終句子 |
| 審查者 | `town-content-reviewer` | 全量審查、查證、漏選檢查、描寫完整度、**對每個 FAIL 指出適用的決議規則編號** | 修改內容檔 |
| 負責人 | 使用者 | 定規則、看結果、推翻自動決議 | 逐條抽查 |

## 2. 流程（每縣市一批）
`①候選池 → ②評分選取 → ③模板撰寫 → ④自檢表 → ⑤lint → ⑥審查者全量審查 → ⑦決議表處理 FAIL → ⑧重審 → ⑨交付`
- ⑥⑦⑧ 最多 **3 輪**；第 3 輪仍未通過者，一律依第 4 節的「降級／刪除」自動決議，標為 auto-resolved；撰寫者不得在未滿 3 輪前自行宣告 auto-resolved。
- auto-resolved 產出的新句（降級／合併）須再接受**一次確認審查**，該次不算新輪，結果只能是 PASS 或刪除（刪除後適用 D10／D11），不得再改寫。補位條目自第 1 輪起算，整批補位嘗試最多 2 次。

### ① 候選池
每區至少 8 個候選、3 種來源類型（官方／百科／媒體旅遊；使用者提供的截圖算一種）。候選池檔：`docs/research/candidate_pools/<縣市>_<區>.md`，每筆記：名稱、一句亮點、來源連結、行政區（依 D9）、**類型（由研究員填，撰寫者換類型須在自檢表註明理由，審查者可否決）**。現有條目一併評分，沒有優先權。

#### ①-a 探索階段：先回答「這個區最有特色的是什麼」（在評分之前）
檢討：新園鄉的問題不在寫不寫某個稱號，而是**我們根本沒確認過這個區最有特色的是什麼**，後面的放或不放評估因此建立在不完整的名單上。探索階段的產出是「**區域特色清單**」，沒有它不得進入 ②。
1. **權威底稿（先讀整頁，不只看摘要）**：以**維基百科該區整頁**（歷史、地理、產業、景點、文化各段）為必讀底稿；官方網站（縣府、公所、文化資產名錄）只在搜尋結果能直接讀到時才用，**不得為了讀官網而要求負責人放行網域**（網路白名單是固定的，不逐區調整）。每份記「已讀全文／只看到摘要／讀取失敗」；官方底稿讀不到不算缺陷，改由第 2 步的多源統計補足，但須標示「官方來源未讀」。
2. **多源頻率統計**：再收集 ≥5 個獨立的旅遊、媒體、在地部落格或地圖評論來源（含搜尋引擎 AI 摘要與使用者截圖，僅當線索）。把所有來源提到的特色逐一記錄，統計「被幾個獨立來源提到」。≥3 個來源都提到的，視為**核心特色**；1–2 個來源的視為**次要特色**。
3. **一句話身份**：用統計結果寫出「這個區以 ___ 、___ 聞名」（核心特色最多 3 個），並附各自的來源數。
4. **缺口自問**：若身份只有「廟、老街、地名由來」這類每區都有的東西，視為搜尋不足，換關鍵字與來源類型重做。
5. **區域特色清單**進入 ② 時，每個核心特色與次要特色都必須有明確去向：入選（寫進條目）、落選（寫原因，例如資訊不足、已有更強者、使用者指定移除）。**核心特色不可無聲消失**；若核心特色沒有入選，須在交付物（第 5 節）逐項說明。
6. **誠實揭露**：若只能讀到摘要或來源不足 5 個，該區標「覆蓋不完整」，列入交付物，不得宣稱已找全。

#### ①-b 覆蓋檢查矩陣（防止資料找不全）
檢討：新園鄉的案例顯示，只用「<區> 特色」這類一兩個關鍵字搜尋，會漏掉農漁產業、地景、廟宇、主題公園等整個面向。因此候選池必須通過**十面向矩陣**，每個面向至少搜尋一次，並在候選池檔逐格寫「查詢字串＋有候選／查無」：
1. 農業作物與特產　2. 漁業與養殖　3. 自然地景與地質　4. 生態（動植物、候鳥）　5. 歷史古蹟與聚落　6. 信仰廟宇與民俗活動　7. 節慶與祭典　8. 飲食小吃　9. 人物、藝術、特殊設施（主題公園、博物館、車站、工廠）　10. 交通與水利（鐵道、港、圳、橋）
來源至少涵蓋：維基百科（含「產業」「景點」段落）、縣市政府或鄉鎮公所旅遊網、2 則以上媒體或旅遊文、搜尋引擎 AI 摘要與使用者提供的截圖（只當線索）。
- **讀取方法**：子代理的 WebFetch 常整批失敗（ENOTFOUND），改用 Bash：`curl -sS -A "ForClaude2-research/1.0 (<聯絡信箱>)" "<網址>"`（維基百科用 `https://zh.wikipedia.org/w/api.php?action=query&prop=extracts&explaintext=1&format=json&redirects=1&titles=<條目名>`，同名條目要用「溪口鄉_(台灣)」這類消歧名；遇 HTTP 429 等待 retry-after 秒再試，並放慢請求）。讀取方法都失敗才可標「讀取失敗」。
- **核心特色必須完整評分**：來源數 ≥3 的特色不得因初步印象直接落選，必須五項逐項評分並寫理由（老街這類熱門項目不得只給一個總分）。
- **來源數計算**：以「獨立網域」為單位（同網域不同頁面算一個；轉載同一新聞稿算一個），統計表列出各來源網域。
- 任何面向「查無」要換 ≥2 組不同關鍵字再確認，才可填查無。
- 使用者曾決定移除的項目留在候選池並標 user-decided，**照常重新評分**：使用者的決定不是絕對的，評分顯示為核心特色（≥3 來源）且總分 ≥7 時，撰寫者須在交付物第 5 節的「建議放回」清單附理由與新句，由使用者決定；使用者未同意前不寫入內容檔。
- **盲測召回**：審查者先**不看**撰寫者的區域特色清單，自己用同一方法列出該區前 5 個特色（含來源數），再與清單比對；核心特色（≥3 來源）缺漏即 FAIL（D17）。
- 審查者的漏選檢查必須**獨立重跑同一矩陣**，並把自己用的查詢字串寫進報告；矩陣有空格沒填、或漏掉審查者找到的 ≥7 分候選，即為 FAIL（走 D17）。

### ② 評分選取
五項各 0／1／2：**吸引人、特色（與同類差在哪）、記憶點（能一句話轉述）、可查證、在地性**。總分 ≥7 且記憶點 ≥1 可入選（補位也一樣：無分數 ≥7 的候選即視為候選池耗盡），每區選最高的 1–3 條；地名由來類必須記憶點=2。落選原因一行寫入候選池檔。「最高」＝總分最高；同分比記憶點，再比可查證，仍同分取候選池檔中較前者。

### ③ 類型模板（每條至少兩項必備資訊）
| 類型 | 必備資訊 |
|---|---|
| 動植物生態 | **外觀**（顏色、體型、形狀）、習性或季節、在此地的特別處 |
| 食物小吃 | 是什麼（主料）、**做法或口感**、與同類差異 |
| 古蹟建築 | 外觀特徵或獨特構造、來歷用途、為何留下 |
| 廟宇民俗活動 | **流程（做什麼）**、特別在哪、週期（每年…） |
| 地景自然 | 看到什麼、成因、特別處 |
| 產業 | 做什麼、怎麼做、為何在此 |
| 地名／傳說 | 只在有故事或反差時；傳說要寫「相傳」並說明缺乏史料 |
**粗體項為必備**：缺任一粗體項即 FAIL（走 D4）；另需至少一項非粗體項。「是什麼（主料）」不算數，必須是句中實際寫出、且有 E2 來源的資訊。不屬於任何模板的項目（如新建景點）歸「地景自然」或「產業」，必備「看到什麼」＋「為何在此」。
**「有畫面」的定義**：句中至少有一個可被看見／聽見／嚐到／做到的具體名詞或動作（顏色、形狀、動作、聲音、味道），且不是名稱、年份、面積、設施清單。
**生態類**：「在此地的特別處」須有 E2 來源指出該地的繁殖、棲息或過境事實；只有物種通論視為 Q2 FAIL。
並遵守手冊：稱號先寫並標 ※、不寫時效用語／特定店名／無出處玩笑、年份有出入不寫死、日常行為要說出特別之處。

### ④ 自檢表、⑤ lint
自檢表每條一行（類型、模板兩項、Q1–Q7、來源、稱號）。`python3 android/tools/town_lint.py`：**E 必為 0**；W 全部交審查者逐條寫處置。

### ⑥ 審查者全量審查
審整個批次，不是只審改動的。必須：逐條 Q1–Q7；查證（見第 3 節，無法查證視為 FAIL）；漏選檢查（自己搜尋「<區> 特色／景點／美食」比對）；描寫完整度；處置每個 lint W；**每個 FAIL 都要標明適用的決議規則編號（D1…）**。

## 3. 證據標準（取代「兩個來源」一刀切）
| 級別 | 適用內容 | 需要的證據 |
|---|---|---|
| E1 | 稱號、排名、「第一／唯一／最／首／全台／少數」等（「最後」「最近」等非稱號用法由審查者逐句判定並寫理由）；「X 之鄉／X 之都」一律視為稱號 | 兩個**各自發布**的來源，並標 ※ |
| E2 | 一般事實（外觀、做法、流程、建築、歷史事件） | 一個官方、百科或知名媒體來源 |
| E3 | 傳說、口述、單一報導 | 寫「相傳／據說／一說」，說明缺乏史料；該說法本身必須有一個可查來源 |
| E4 | 會變動的數字（數量、造價、人數、比例） | 不寫單一數字；寫區間或不寫。排名句同時適用 E1 與 E4：須滿足 E1 兩來源，且改寫成不含逐年變動數字的說法（如「長年是主要產區之一」），並標 ※ |
「**各自發布**」：同一份新聞稿、轉載同一評選、媒體引用官方資料，都只算一個來源。
「**曾被報導為…**」：只要查證「該報導存在」（一個來源）即可，標 ※，句中不得改寫成事實。
**工具限制**：搜尋只回摘要。摘要中能看到內容支持就算「已查證」；看不到就是「無法查證」。「僅閱讀」沒有查證，不算通過。
**使用者提供的資訊**：視為線索；需要至少一個可查來源才寫入；查不到（同一說法已用 ≥3 個不同關鍵字搜尋仍無來源）→ 依 D1 去掉該說法，並登記 S3 請使用者補來源；**不阻擋批次**。

## 4. 決議表（取代「需要你決定」）
每個 FAIL 依下表處理，不問負責人。**同一條目符合多條時依序處理：D9→D2→D1/D14/D3→D7→D6→D5→D4/D16→D8→D13→D10→D11**；處理後條目仍存在，重新比對 Q1–Q7。
**user-decided 的「不補替代」優先於 D6／D11 的補位**（該區仍受 D10）。
| 編號 | 情況 | 自動決議 |
|---|---|---|
| D1 | 稱號只有一個來源，或零來源（含使用者所稱） | 去掉稱號，改寫成事實；若「報導存在」可查，改用「曾被報導為…」＋※ |
| D2 | 來源互相矛盾（年份、數字、名稱；行政區見 D9） | 不選邊：拿掉有爭議的部分，只寫共識；整條只剩爭議則刪 |
| D3 | 數字會變動 | 區間或不寫（E4） |
| D4 | 缺模板必備資訊（外觀／做法／流程）；Q4 FAIL | 通用額度內搜尋補；補不到→換候選；候選都缺→刪（受 D10 約束） |
| D5 | 設施／項目清單、沒有畫面 | 在通用額度內至少一次針對「反差或具體畫面」搜尋；沒有→刪（受 D10 約束） |
| D6 | 兩條同主題或高度重複（如兩條酸菜） | **合併成一條**，保留資訊最多的寫法，空出的位置從候選池補位。「同主題」＝共用同一主要名詞，或同一產業鏈（原料與其工具）；合併句須含兩條各一項必備資訊且 ≤90 字，並重新查證 |
| D7 | 單一來源傳說 | 依 E3 改寫；若改寫後沒有畫面→刪 |
| D8 | 地名由來沒有故事或反差 | 刪 |
| D9 | 行政區衝突（官方地址 vs 地圖 vs 來源，含 D2 的行政區部分） | 優先順序：使用者先前明示的決定（台帳登記為 user-decided）→ 官方地址與 Google 地圖一致者 → 官方地址（＝該景點管理機關公告者）；所在地不在路線（`TAIWAN_LOOP.md` 列出的鄉鎮）上的不放 |
| D10 | 刪除後該區剩 0 條 | 禁止刪光：保留最強的一條，降級成「只寫 E2 事實、去稱號」版本，標 auto-resolved。降級版可豁免 Q2、Q4、Q5、手冊禁止第 7 項，**不得**豁免 E1–E4、行政區、禁止第 1–5 項、格式；且仍須有至少一項可驗證的具體外觀或做法。若連這樣的內容都找不到，在候選池檔登記「無可寫內容」，**允許該區 0 條**（唯一允許 0 條的情況） |
| D11 | 該區條目 <2 | 從候選池補位（僅限分數 ≥7）；候選池耗盡→在候選池檔記錄後允許 1 條 |
| D12 | 外部意見（AI、截圖）與已驗證證據衝突 | 以驗證證據為準，不採用外部意見，並在台帳寫明 |
| D13 | lint W（稱號同義詞、時效、玩笑、籠統形容、地名由來） | 逐條判：「別稱」僅限官方文件或字典可查者；「非現況」「有出處」（句中玩笑或形容有明確來源）→放行並寫理由；其餘先改寫一次，仍不過則刪。「X 之鄉／X 之都」不得以別稱放行，走 E1／D1 |
| D14 | 稱號類內容在 3 輪後仍無第二來源 | 去稱號，降成事實（D1） |
| D15 | 審查者判 FAIL、但決議表沒有適用規則 | 觸發 S1。撰寫者可自動套用的新規則限於「比現有規則更嚴格，或只補操作細節」者，寫進本表並登記供負責人推翻；放寬手冊或 E 級標準的新規則須核可，核可前該條標為 blocked |
| D17 | 區域特色清單缺核心特色、覆蓋矩陣缺格、或審查者找到候選池沒有的高分候選 | 補搜尋並加入候選池重新評分；本批次重新做 ②，視同新一輪（不計入 3 輪上限，最多重做 1 次） |
| D16 | Q1、Q2、Q3、Q5、Q6、Q7 或禁止第 1–6 項的 FAIL | 通用額度內搜尋補足；補不到→換候選；候選都不過→刪（受 D10 約束） |

## 5. 交付物（給負責人，每縣市一份）
1. 每區最終列表（完整句子）。
2. 每區**區域特色清單**（一句話身份、各特色來源數與去向）＋候選池摘要：入選＋分數、落選＋原因；標示「覆蓋不完整」的區。
3. 審查者統計（PASS／FAIL／輪次）。
4. **auto-resolved 清單**：每項寫「適用規則編號、做了什麼、原句、新句」，負責人可推翻（推翻後該個案登記為「使用者指定」，之後 D9 優先採用）。
5. 停止條件清單（若有）。
負責人不需要逐條查證。

## 6. 停止條件（只有這些情況才可以問負責人）
- **S1**：決議表沒有涵蓋、且新規則會放寬既有標準的情況（核可前該條標為 blocked，維持原句並登記）。
- **S2**：證據與負責人先前**明示決定**衝突（例如他說「保留」，但來源只有單一傳說）；只回報衝突，不擅自改。
- **S3**：負責人提供的資訊已用 ≥3 個不同關鍵字仍查不到來源。預設處置：不寫入該說法，批次照常完成。
- **S4**：同一批次自動刪除或合併減少的條目超過批次開始時條目數的 30%（補位新增不抵銷）。這是通知性停止：寫進交付物後繼續，不等回覆。

## 7. 台帳
`docs/research/fail_ledger.md`：每個 FAIL／無法查證／漏選／lint W 一列：ID、條目、問題、適用規則、處理、狀態。狀態只有：open、fixed（待審查者確認）、closed（審查者確認）、auto-resolved（第 3 輪後依規則處理，且已過確認審查）、user-decided、blocked（S1／S2／S3 觸發，附安全預設處置：S1 維持原句並標記、S2 維持負責人決定、S3 不寫入該說法）。**批次完成條件：open＝0、fixed＝0；blocked 項已列入第 5 節第 5 點。** 狀態 closed 只能由審查者的判定改寫。

## 8. 原子化操作（防止「檔案、台帳、提交不一致」）
1. 所有內容修改用同一支變更腳本：**先在記憶體套用 → 驗證 → 通過才寫檔**，驗證失敗不得留下任何改動。
2. 提交一律用 `android/tools/safe_commit.sh "訊息"`：lint 有 E 就拒絕提交。
3. 台帳與「原／新」對照檔由變更腳本的紀錄產生，不手寫。
4. 內容檔有變就要重建字型子集（變更腳本內含）。

## 9. 防回歸
- 任何修改都重跑 lint，並重審**該區全部條目**。
- 發佈前全檔審查，FAIL＝0 或全為 auto-resolved／user-decided。
- 負責人每提出新意見：①寫成規則（進手冊或決議表）②進 lint 或審查清單③全檔重掃④掃出的條目登記進台帳。
- 審查者報告若出現「需要負責人決定」，視為 SOP 缺陷：必須新增或修正決議規則（S1）。

## 10. 執行順序
1. 先做條目最少的縣市（現況 20 區只剩 1 條），再依路線順序做其餘縣市。
2. 每批次結束只交付第 5 節的內容；下一批次不等待回覆，直到觸發停止條件為止。
3. 全部批次完成後做全檔審查，再交付總表。
