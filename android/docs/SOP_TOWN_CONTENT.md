# 鄉鎮特色內容作業流程（SOP v2）

目的：讓「是否夠吸引人、有特色、有記憶點、查證是否可靠」由流程保證，而不是靠負責人逐條抽查。本 SOP 取代 `REVIEW_HANDBOOK.md` 第七節的流程；手冊仍是各項規則的完整清單。

## 一、為什麼需要改（第十四輪檢討的結論）
詳見 `docs/research/process_postmortem.md`。三個根本原因：
1. **FAIL 沒有台帳、沒有關閉條件**：審查者第一輪判了 130 條 FAIL，我只處理了其中約一半就往下走，之後每輪只審「被改的條目」，沒審的 FAIL 永遠留在檔案裡（例如民雄鬼屋、酸菜醃桶、三元宮）。
2. **沒有候選池與「選得好不好」的檢查**：審查者只判斷「這一條合不合格」，不判斷「這一區有沒有更好的選擇」。結果是每區只剩下剛好合格的條目（苓雅只剩地名由來、斗南只剩車站）。
3. **審查標準缺少「描寫完整度」與「查證強度」門檻**：高蹺鴴只寫粉紅長腳也 PASS；大量 PASS 只是「僅閱讀」。

## 二、角色
| 角色 | 誰 | 職責 | 不得 |
|---|---|---|---|
| 撰寫者 | 主 Claude | 建候選池、評分、寫句子、修 FAIL、維護台帳 | 自己宣布通過 |
| 研究員 | subagent（可平行多個，每個負責一個縣市） | 只做「候選池」：每區蒐集候選與來源，寫入候選池檔 | 寫最終句子 |
| 審查者 | `town-content-reviewer` | 全量審查、查證、漏選檢查、描寫完整度檢查 | 修改內容檔 |
| 負責人 | 使用者 | 只看「已通過」的完整列表與例外清單 | 不需逐條抽查 |

## 三、流程（每個縣市一個批次）
```
①候選池 → ②評分選取 → ③依類型模板撰寫 → ④自檢表 → ⑤lint → ⑥審查者全量審查 → ⑦台帳關閉 → ⑧給負責人
```

### ① 候選池（研究員）
- 每區至少 **8 個候選**，來源至少 **3 種類型**：官方（公所／觀光署／文化資產網）、百科（維基）、媒體或旅遊；負責人提供的 Google 摘要與截圖也算一種來源。
- 候選池檔：`docs/research/candidate_pools/<縣市>_<區>.md`，每個候選寫：名稱、一句話亮點、來源（連結）、所在行政區（以官方地址／Google 地圖為準）、類型（動植物／食物／古蹟／民俗／地景／產業／地名）。
- 現有條目也要放進候選池一起評分，不享有優先權。

### ② 評分選取（撰寫者）
每個候選對五項各打 0／1／2：**吸引人、特色（與同類差在哪）、記憶點（能一句話轉述）、可查證（≥2 個來源或 1 個官方）、在地性（確實在本區）**。
- 總分 ≥7 且「記憶點」≥1 才可入選；每區選分數最高的 1–3 條。
- 地名由來類：只有「有故事或反差」（記憶點=2）才可入選。
- 不足 2 條時，必須在候選池檔寫明「候選池已耗盡」與每個落選原因；**沒有這份紀錄，lint 的 F11 視為未通過**。
- 落選原因也要列入給負責人的表（見⑧），負責人不必再問「為什麼沒選 X」。

### ③ 依類型模板撰寫
每條至少要有下列模板中 **兩項**：
| 類型 | 必備資訊 |
|---|---|
| 動植物／生態 | **外觀**（顏色、體型、形狀）＋ 習性或季節 ＋ 在此地的特別之處 |
| 食物小吃 | 是什麼（主料）＋ **做法或口感／怎麼吃** ＋ 與同類的差異 |
| 古蹟建築 | 外觀特徵或獨特構造 ＋ 來歷用途 ＋ 為何留下 |
| 廟宇民俗活動 | **做什麼（流程）** ＋ 特別在哪（與同類差異）＋ 週期（每年…） |
| 地景自然 | 看到什麼（形狀、顏色、規模以區間表示）＋ 成因 ＋ 特別處 |
| 產業 | 做什麼 ＋ 怎麼做 ＋ 為何在此地 |
| 地名 | 只在有故事或反差時寫 |
| 傳說 | 只在有可查出處時寫，且寫「相傳」 |
另外沿用手冊：稱號先寫並標 ※、不寫時效用語、不寫特定店名、不寫無出處玩笑、年份有出入不寫死、日常行為要說出特別之處。

### ④ 自檢表（撰寫者，每條一行）
`條目｜類型｜模板兩項是哪兩項｜Q1–Q7 是否通過｜來源 1／來源 2｜稱號是否有 ※`。自檢表隨批次一起送審；空白或敷衍的條目視為未通過。

### ⑤ lint（機械檢查，必須先過）
`python3 android/tools/town_lint.py`
- **E（錯誤）必須為 0**：格式、字數、禁字、備註外洩、缺句號。
- **W（警告）一律交給審查者逐條處理**：稱號同義詞（F3）、時效用語（F4）、玩笑比喻（F7）、籠統形容（F9）、地名由來（F10）、資訊量偏少（F12）、區內條目不足（F11）。審查者必須對每個 W 寫處置（改／可保留的理由）。

### ⑥ 審查者全量審查
審查者每次都要審 **整個縣市批次的全部條目**（不是只審改動的），並做：
1. 逐條 Q1–Q7、模板完整度、來源與行政區。
2. **查證強度**：每條至少要有「已查證」；只有「僅閱讀」的判為 **FAIL（未驗證）**，除非該條屬審查者列出的低風險類型且寫明理由。
3. **漏選檢查**：對每區自己搜尋「<區名> 特色／景點／美食」，比較搜尋結果的前幾名與本區入選條目；若有明顯更強的候選未入選，回報「漏選」，由撰寫者回候選池補評。
4. **描寫完整度**：動植物有沒有外觀、食物有沒有做法或口感、活動有沒有流程。
5. 逐條處置 lint 的 W。
6. 輸出：逐條判定（PASS 已查證／FAIL／無法查證）、漏選清單、W 處置表。

### ⑦ 台帳（`docs/research/fail_ledger.md`）
- 撰寫者把審查者每一個 FAIL、無法查證、漏選、W 都登記成一列：ID、條目、問題、狀態（open／closed／exception）、處理說明、關閉時的審查者判定。
- **只有台帳 open = 0 才算批次完成**；無法關閉的列要改成 exception，附上理由與需要負責人決定的事項（例如單一來源但負責人想保留）。
- 關閉必須由審查者在下一輪確認（不是撰寫者自己宣布）。

### ⑧ 給負責人的內容
每個縣市一份，只包含：
1. 每區最終列表（完整句子）。
2. 每區的**候選池摘要**：入選條目＋分數、落選條目＋落選原因（一行）。
3. 審查者的最終判定統計與漏選結果。
4. exception 清單（需要你決定的事）。
負責人不需要再逐條查詢；若不同意，只需對 exception 或落選原因表態。

## 四、防回歸規則
- 任何修改（含單條）都要重跑 lint；改動所在整個「區」要重審，不是只審那一條。
- 發佈（合併進 App）前必須跑一次**全檔**審查，統計 FAIL=0（或全為 exception）。
- 手冊或 SOP 有新增規則時，要同步更新 `town_lint.py` 或審查者的檢查清單；寫不成機械規則的，列入審查者清單。
- 每次負責人提出新意見，不是只修該條，而是：①寫成規則 ②放進 lint 或審查清單 ③全檔重掃一次 ④把掃出的其他條目登記進台帳。
